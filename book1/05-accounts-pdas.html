Part 5 · On-chain

Accounts and PDAs

Where everything lives on Solana: which accounts a launchpad needs, and why most of them have addresses nobody holds a key for.

1. Everyday analogy2. Design question3. Simple explanation4. The math5. TypeScript code6. TypeScript exercise7. Architecture diagram8. Sources

1 Everyday analogy

In Lagos, you can find a house from its street name and plot number. Anyone who knows "Plot 12, Adeola Odeku Street" can find it, and nobody needs a secret. A PDA (program-derived address) is like that. Anyone can work out the address from public "seeds" such as "bonding-curve" + the mint.

But the house's safe can only be opened by one bank. There is no key, so a person can't open it. A PDA has no private key, and only the program it was derived from can sign for it. That makes it a perfect place to keep a curve's SOL and tokens.

2 Design question

For each coin, you need to store its curve numbers, hold its SOL, and hold its unsold tokens. Where should each of these live, who should own them, and how does a website find them without asking a server?

Try to answer on your own first, in plain English. A gut answer is fine.

Reveal answer

Put them in program-owned accounts at PDAs, derived from fixed seeds plus the mint.

  • pump.fun Real: pump.fun docs: the Global account lives at the PDA from ["global"]. Each coin's curve lives at the PDA from ["bonding-curve", mint].
  • Meteora DBC Real: Meteora DBC repo: a pool lives at ["pool", config, max(mint_a, mint_b), min(mint_a, mint_b)], and each vault at ["token_vault", mint, pool]. A single pool_authority PDA owns the vaults and is the mint authority. The partner's config is a normal keypair account, not a PDA.

Any website can derive the same addresses locally, so there's no server lookup and no trust needed.

3 Simple explanation

  • Account: a box of bytes on Solana with an owner program. Only the owner program can change its data.
  • PDA: an address computed from seeds and a program ID that is guaranteed not to be on the Ed25519 curve, so no private key exists for it. Only that program can sign for it, through invoke_signed Real: Solana docs.
  • Bump: derivation tries bump values from 255 downwards until the hash lands off the curve. The first bump that works is the canonical one, and you should store it and reuse it.
  • Why max/min in Meteora's seeds? Sorting the two mints means the pool for (A, B) and (B, A) is the same address, so one pair can never get two pools.

4 The math

Simplified PDA derivation (see the Solana docs for the exact byte layout):

PDA=SHA256(seed1 ∥ … ∥ seedn ∥ bump ∥ programId ∥ "ProgramDerivedAddress")\text{PDA} = \text{SHA256}(\text{seed}_1 \,\|\, \dots \,\|\, \text{seed}_n \,\|\, \text{bump} \,\|\, \text{programId} \,\|\, \texttt{"ProgramDerivedAddress"})PDA=SHA256(seed1​∥…∥seedn​∥bump∥programId∥"ProgramDerivedAddress")

The result must not be a valid Ed25519 public key. Limits Real: Solana docs: at most 16 seeds, each up to 32 bytes, and a bump from 0 to 255.

We checked this in code: deriving ["global"] under pump.fun's program 6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P gives 4wTV1YmiEkRvAtNtsSGPtUrqRYQMe5SKy2uB4Jjaxnjf, the exact Global address in pump.fun's docs.

5 TypeScript code

Derive pump.fun's public PDAs with @solana/kit. This is a real derivation, and it was tested against the documented address:

code/pdas.ts
// Chapter 5 — deriving pump.fun's public PDAs with @solana/kit.
import { address, getAddressEncoder, getProgramDerivedAddress, type Address } from "@solana/kit";
export const PUMP_PROGRAM_ID = address("6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P");

export async function globalPda(): Promise<Address> {
  const [pda] = await getProgramDerivedAddress({ programAddress: PUMP_PROGRAM_ID, seeds: ["global"] });
  return pda;
}
export async function bondingCurvePda(mint: Address): Promise<Address> {
  const [pda] = await getProgramDerivedAddress({
    programAddress: PUMP_PROGRAM_ID,
    seeds: ["bonding-curve", getAddressEncoder().encode(mint)],
  });
  return pda;
}

The Meteora-style seed order General pattern / our clone (our TypeScript, following the seed list from Meteora's repo):

our clone: sorted-mint pool seeds
import { getAddressEncoder, type Address } from "@solana/kit";
const enc = getAddressEncoder();
function cmpBytes(a: Uint8Array, b: Uint8Array) {
  for (let i = 0; i < 32; i++) if (a[i] !== b[i]) return a[i] - b[i];
  return 0;
}
export function poolSeeds(config: Address, mintA: Address, mintB: Address) {
  const a = enc.encode(mintA), b = enc.encode(mintB);
  const [hi, lo] = cmpBytes(a, b) > 0 ? [a, b] : [b, a];
  return ["pool", enc.encode(config), hi, lo];
}

6 TypeScript exercise

Using pdas.ts, derive the bonding-curve PDA for any mint you like. Then write a test proving that poolSeeds(config, A, B) and poolSeeds(config, B, A) give the same seeds, and so the same PDA.

Show a solution

Call getProgramDerivedAddress({ programAddress, seeds: poolSeeds(cfg, A, B) }) twice with the mints swapped and assert that the two addresses are equal. Sorting makes the order of the inputs irrelevant.
